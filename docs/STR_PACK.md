# The UI strings: what a dictionary could give (AC791N build)

Generated by `tools/str_pack.py` from `build/felucca.elf`: class **TARGET**, the linker's own
bytes, not an estimate.

| | bytes |
|---|---|
| `.rodata.str1.1` | 25580 |
| text of the literals | 25580 |
| literals | 2277 |
| duplicate literals left | 0 |
| tail sharing still available | 0 |
| prefix (radix tree) | 8698 |
| accessor variant (radix + 2 B index per literal) | 4144 |

The strings are addressed by 4-byte link-time constants inside `.text`, which is the XIP flash:
a string built at boot cannot be reached by those words. Each rebuilt string therefore costs a
4-byte pointer slot in RAM (9108 B for these 2277 literals) or an index passed at every call site --
and the expanded text itself needs somewhere to live (25580 B against the 4 128 B free in RAMTEXT).

## The four schemes, and what each one really costs

| scheme | XIP saved | RAM it needs | verdict |
|---|---|---|---|
| identical literals | 0 (the linker already folds them: **0 duplicates left**) | 0 | done by ld |
| shared **tails** (`"MORPH CHORD"` / `"CHORD"`) | **0 B, 0 pairs left** | 0 | done by ld (`SHF_MERGE\|SHF_STRINGS` merges suffixes too) |
| **prefix dictionary + boot expansion** | 8 698 B of text (radix: 25 580 → 16 882) | **9 108 B** of pointer slots + 25 580 B of text | impossible: 4 128 B free in RAMTEXT |
| prefix dictionary through an **accessor** (index per literal, expanded into a small stack buffer) | 4 144 B net (16 882 B of text + 4 554 B of indexes) | 0 | a net loss: see the code cost below |

### Why the boot expansion cannot work

The whole idea rides on one fact: a literal is reached by a **4-byte link-time constant**. In this image
**4 289 of the 4 296 words** that point into `.rodata.str1.1` sit inside the XIP flash (`.text`, at
0x02000120..0x208cc90, read-only); only 7 sit in RAM. A value the linker wrote into flash cannot be repointed
at boot, so an expanded string needs either a pointer slot in RAM (4 B × 2 277 = 9 108 B, plus the text itself)
or an index at every use. RAMTEXT has 4 128 B free: the expansion does not fit, and no other window has 25 KB
of headroom under its floor.

### Why the accessor, which needs no RAM, still loses

Measured with the project's own compiler (`pi32v2/bin/clang -target pi32v2 -Os`, 8 call sites each side,
`draw(x, y, "CUTOFF")` against `draw(x, y, txt(id, buf))`):

| variant | `.text` per call site | `.rodata.str1.1` |
|---|---|---|
| literal argument | 14.5 B | 58 B for those literals |
| index + accessor | 19.2 B | 0 |

**+4.7 B of code at every call site.** The firmware uses ~5 992 literal occurrences in `firmware/src`: the
accessor would add roughly 28 KB of code to save 4 144 B of data -- a net loss of about 24 KB. Break-even would
need fewer than 880 call sites, and there are six times that.

So the strings are left as the linker laid them: 25 580 B, no redundancy left to take by folding, and no way to
re-encode them that is cheaper than it looks.
